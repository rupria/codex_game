## 1. 결론

현재 흐름에는 서버가 필요하지 않다. 게임 상태, AI 반응, 카드 덱, 포커 판정, 아이템과 HP를 모두 클라이언트 안에서 처리하고 정적 파일로 웹 배포할 수 있다.

1순위 기술 스택은 다음과 같다.

| 구분 | 선택 | 이유 |
|---|---|---|
| 엔진 | Godot 4.6 표준판 | 하나의 프로젝트에서 브라우저와 Windows 설치 빌드를 함께 준비할 수 있고 UI, 애니메이션과 3D 물리를 한 엔진 안에서 처리할 수 있다. |
| 스크립트 | GDScript | Godot 4의 C# 프로젝트는 Web export를 지원하지 않으므로 표준판과 GDScript를 사용한다. |
| 웹 렌더러 | Compatibility | Godot 4 Web export는 WebGL 2.0과 Compatibility 렌더러를 사용한다. |
| Web export | 단일 스레드 | 별도 교차 출처 격리 헤더 없이 정적 호스팅하기 쉽고 호환성이 높다. |
| 3D 물리 | Godot 내장 3D 물리 | 카드 낙하, 뒤집기, 벨 눌림과 충돌 연출을 `RigidBody3D`, `StaticBody3D`, `Area3D`로 시험한다. |
| 배포 | 정적 HTTPS 호스팅 | `.html`, `.js`, `.wasm`, `.pck`를 공개 URL에 배포하며 로그인과 백엔드를 사용하지 않는다. |
| 설치 빌드 | Windows x86_64 export preset | 웹 우선 검증 후 같은 프로젝트에서 실행 파일을 생성한다. 실제 `pub` 반영은 별도 승인 후 진행한다. |

이 선택은 엔진 확정이 아니라 1순위 제안이다. 아래 기술 스파이크를 통과하면 확정한다.

## 2. 흐름에서 확인된 구현 범위

### 주요 상태

```text
MAIN_MENU
-> ROUND_SETUP
-> FIRST_PUBLIC_CARD
-> READY_TO_FLIP
-> FLIP_ANIMATION
-> BELL_WINDOW
-> BELL_RESOLVE
-> ACQUIRE_RESOLVE
-> READY_TO_FLIP 또는 HALLI_END
-> PRIVATE_CARD_NORMALIZE
-> LAST_PUBLIC_CARD
-> ITEM_WINDOW
-> HAND_LOCKED
-> POKER_SHOWDOWN
-> REWARD_AND_DAMAGE
-> ROUND_SETUP 또는 BATTLE_END
-> NEXT_STAGE 또는 MAIN_MENU
```

### 입력

- `W` 또는 중앙 영역 클릭: 다음 카드 펼치기
- `Q` 또는 왼쪽 영역 클릭: 왼쪽 벨
- `E` 또는 오른쪽 영역 클릭: 오른쪽 벨
- 카드 3장 정리, 아이템 사용과 패 확정: 우선 마우스로 구현
- 마우스와 키보드는 동일한 `InputRouter` 명령으로 변환해 판정 차이를 없앤다.
- 모바일 지원이 확정되면 같은 영역에 터치 입력을 연결한다.

### 핵심 시스템

- 표준 52장 단일 덱과 사용 카드 추적
- 좌우 카드 펼치기와 해골 합계 3 판정
- 제한 시간과 AI 반응 예약
- 오조작, 동시 입력과 벨 승패 처리
- 먼저 3승한 참가자의 할리갈리 단계 종료
- 개인 카드 3장 선택 또는 무작위 보충
- 5장 포커 족보와 동률 비교
- 아이템 사용 창, 패 확정, HP와 스테이지 분기
- 최대 26회 펼치기 도달 시 진행 보장

## 3. 3D 물리 적용 원칙

3D 물리는 가능하지만 게임 규칙의 기준으로 사용하지 않는다.

- 카드가 떨어지고 튀거나 벨이 눌리는 모습은 물리 연출로 구현할 수 있다.
- 카드의 논리 위치, 공개 순서, 해골 합계, 입력 시각, 승패와 획득 결과는 상태 머신이 결정한다.
- 물리 오브젝트가 목표 위치에 도달하지 못해도 타임아웃 후 논리 상태를 기준으로 연출을 완료한다.
- 카드 판정 중에는 관련 입력을 잠그고 연출 완료 신호 뒤에만 다음 상태로 이동한다.
- 물리 업데이트는 기본 고정 틱을 사용하고, 브라우저 프레임 저하가 판정 시간에 영향을 주지 않도록 단조 증가 시간 기준 타이머를 사용한다.
- Web export 기본 템플릿에서 호환성 부담이 큰 외부 GDExtension 물리 플러그인은 초기 범위에서 제외한다.
- 충돌 형상은 단순한 상자 위주로 사용하고 한 화면의 활성 RigidBody 수를 제한한다.

이 분리는 브라우저별 물리 오차와 저사양 프레임 저하가 카드 승패를 바꾸는 문제를 방지한다.

## 4. 프로젝트 구조 제안

실제 게임 프로젝트는 역할 규칙에 따라 `programer` 아래에 둔다.

```text
programer/
├─ game/
│  ├─ project.godot
│  ├─ export_presets.cfg
│  ├─ scenes/
│  │  ├─ main_menu/
│  │  ├─ battle/
│  │  └─ ui/
│  ├─ scripts/
│  │  ├─ state/
│  │  ├─ cards/
│  │  ├─ poker/
│  │  ├─ ai/
│  │  ├─ input/
│  │  └─ items/
│  ├─ assets/
│  └─ tests/
└─ 문서 파일
```

생성물은 저장소의 기존 `.gitignore`에 따라 `build/`, `dist/`, `tmp/`에 두고 `dev` 소스 커밋에 포함하지 않는다. 배포 산출물과 공개 URL은 사용자 승인 이후 `pub` 운영 절차에서 다룬다.

## 5. 필요한 개발 환경

### 필수

- Godot 4.6 표준판과 동일 버전 export templates
- Git
- 최신 64비트 Chromium 계열 브라우저 1종 이상
- Firefox 최신 안정판
- 정적 로컬 HTTP 서버 또는 Godot Web 원클릭 테스트 환경

현재 PC의 PATH에서는 Godot 실행 파일이 확인되지 않았다. 구현 시작 전에 Godot 설치 위치와 팀 공통 버전을 고정해야 한다.

### 선택

- Blender: 3D 카드, 벨과 테이블 모델을 직접 제작할 때만 사용
- 이미지 편집 도구: 카드 및 UI 텍스처 제작
- 브라우저 개발자 도구: WebGL, WebAssembly, 입력과 로딩 오류 확인

Node.js, 데이터베이스와 별도 API 서버는 현재 게임 실행에 필요하지 않다. 배포 자동화 도구가 선택될 때만 보조 환경으로 추가한다.

## 6. Web export 및 공개 링크 조건

- WebAssembly와 WebGL 2.0을 지원하는 브라우저를 대상으로 한다.
- `Compatibility` 렌더러와 단일 스레드 Web export를 사용한다.
- 시작 파일은 `index.html`로 내보내고 함께 생성된 파일 이름을 임의로 바꾸지 않는다.
- 호스팅은 `.wasm`에 올바른 MIME type을 제공해야 한다.
- 공개 HTTPS URL은 초대, 로그인, 개별 승인, 결제와 비밀키 없이 열려야 한다.
- 첫 화면에 목표와 `Q-W-E`/마우스 조작을 표시한다.
- 서비스 워커 캐시로 이전 빌드가 보일 수 있으므로 배포 버전 또는 캐시 갱신 절차를 둔다.
- 모바일 브라우저는 성능 제약이 더 크므로 초기 필수 지원 여부를 기획에서 확정한 뒤 별도 검증한다.

## 7. Windows 설치 빌드 준비

- Web과 같은 Godot 프로젝트에 `Windows Desktop` x86_64 export preset을 둔다.
- 파일 접근, 화면 크기와 입력 처리는 플랫폼 분기를 최소화한다.
- 웹에서 지원되지 않는 기능을 코어 플레이에 넣지 않는다.
- 저장 기능이 추가되더라도 서버 계정 대신 로컬 저장부터 검토한다.
- 실행 파일, `.pck`, 서명과 배포 패키지는 웹 빌드 검증 이후 준비한다.
- `pub`에 실행 파일 또는 통합 빌드를 올리는 작업은 사용자 명시 승인 전 수행하지 않는다.

## 8. 구현 전 기획 확정 필요 사항

다음 항목은 프로그래머가 임의로 확정하지 않는다.

### P0

- 제한 시간의 길이, 시작·정지·재개와 시간 초과 결과
- 오조작 시 해당 판정 패배 외의 추가 페널티
- 플레이어와 AI 입력이 같은 시각일 때의 처리
- 획득 카드가 판정 카드 전체인지 최상단 1장인지
- 26회 제한 도달 시 보충과 버리기 규칙
- 5장 포커 동률 처리

### P1

- 정답을 고의로 누르지 않는 플레이 허용 여부
- AI 반응 시간, 오답률과 카드 선택 성향
- 시작 HP, 피해량, 아이템 종류와 사용 한도
- 지원 브라우저, 모바일 포함 여부, 최소 화면 크기와 화면 방향

P0는 상태 머신과 데이터 모델에 직접 영향을 주므로 코어 프로토타입 완료 전에 결정되어야 한다.

## 9. 기술 스파이크 통과 기준

Godot 채택 전에 작은 별도 장면으로 다음을 확인한다.

- [ ] 빈 캐시의 공개 또는 로컬 HTTPS 환경에서 Web build가 정상 로드된다.
- [ ] `W`, `Q`, `E`, 마우스 입력이 상태별로 한 번만 처리된다.
- [ ] 3D 카드 10장 이상을 펼치고 벨 충돌 연출을 반복해도 진행이 멈추지 않는다.
- [ ] 물리 프레임이 낮아져도 논리 타이머와 벨 승패가 변하지 않는다.
- [ ] 창 크기 변경 시 카드, 벨과 첫 화면 안내가 잘리지 않는다.
- [ ] Chrome/Edge와 Firefox에서 동일한 코어 입력 결과를 얻는다.
- [ ] Windows x86_64 테스트 export가 같은 상태 흐름으로 실행된다.
- [ ] 초기 다운로드 크기와 첫 입력 가능 시간을 기록한다.

스파이크가 실패하면 대안으로 `TypeScript + Babylon.js 또는 Three.js + Rapier + Vite`를 비교한다. 이 대안은 웹 코드 제어는 직접적이지만 3D, 물리, UI와 설치 패키징을 여러 도구로 조합해야 하므로 현재는 2순위다.

## 12. Codex 활용 기록

- 문제: 최신 게임 진행 흐름을 웹 필수 제출, 설치 빌드 가능성과 3D 물리 요구에 맞는 기술 구조로 변환해야 했다.
- Codex 사용: PDF 전체 렌더링, PDF 텍스트와 XMind 계층 추출, Markdown·연계 명세 대조, 공식 엔진 문서 확인과 기술 위험 분류에 사용했다.
- 사람의 결정: 서버는 사용하지 않고 3D 물리 가능성을 고려하며, Git 푸시는 사용자 사전 승인 후에만 진행하도록 지시했다.
- 결과: Godot 기반 1순위 환경, 연출과 판정 분리 원칙, 기술 스파이크와 기획 확정 항목을 문서화했다.

## 13. 현재 작업 상태

- 기술 검토 문서 작성 완료
- 게임 코드와 엔진 프로젝트는 아직 생성하지 않음
- Godot은 현재 PATH에서 확인되지 않음
- 커밋·푸시·`pub` 반영은 수행하지 않음
