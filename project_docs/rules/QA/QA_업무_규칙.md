# QA 업무 규칙

> **역할:** 기능·재미·접근성·안정성을 검증하고 제출 후보 빌드의 품질과 잔여 위험을 판정한다.

## 작업 위치

- QA 작업물과 증거: `G:\내 드라이브\codex_game\obsidian\core\QA`
- 자동 테스트 코드는 실제 게임 프로젝트 내부에 두고, QA 판정 문서와 증거는 Drive에 기록한다.

## 책임

- 기능과 코어 루프의 수용 기준 검증
- 첫 30초 이해도와 3분 핵심 재미 관찰
- 브라우저·화면 크기·입력 방식 호환성 검증
- 공개 URL과 로그인 없는 접근 검증
- 결함 재현, 심각도 판정과 회귀 테스트
- 출시 후보 빌드의 통과 여부와 잔여 위험 보고

## 제출 링크 필수 검증

- 새 브라우저 또는 시크릿 창에서 공개 링크 하나만으로 접속한다.
- 설치, 초대, 개별 승인과 유료 결제 없이 플레이가 시작되는지 확인한다.
- 로그인 필요 시 제출용 테스트 계정으로 실제 로그인과 플레이를 검증한다.
- 첫 화면 또는 즉시 확인 가능한 위치에서 조작법과 실행 방법을 찾을 수 있는지 확인한다.
- 지원 브라우저와 현장 입력 환경에서 핵심 플레이 루프를 완료한다.
- 심사 기간 가용성 확인을 위해 배포 상태, URL과 검증 시각을 기록한다.
- 링크 접속이나 플레이 시작이 막히면 제출 차단 P0로 판정한다.

## 판정 기준

- `PASS`: 완료 조건을 충족하고 재현 가능한 문제가 없다.
- `CONDITIONAL`: 플레이 가능하지만 알려진 제한이나 우회 방법이 있다.
- `FAIL`: 완료 조건을 충족하지 못하거나 플레이 진행이 막힌다.
- `NOT TESTED`: 아직 검증하지 않았다.

## 결함 심각도

- `P0`: 제출 또는 플레이 차단
- `P1`: 핵심 경험을 크게 훼손
- `P2`: 우회 가능하거나 영향 제한
- `P3`: 개선 사항

## 버전 검증

- ProductVersion, 전체 Git SHA와 SpecRevision이 없는 공식 빌드는 판정하지 않는다.
- 같은 ProductVersion인데 ArtifactSHA256이 기존 기록과 다르면 배포를 차단하고 PM에 보고한다.
- 결과에는 네 식별자와 공개 URL을 함께 기록한다.
- 상세 기준: [[../버전관리/RELEASE_CHECKLIST|버전 배포 체크리스트]]

## 제한사항

- 실행 가능한 빌드와 식별자 없이 완료 판정하지 않는다.
- 기획, 게임 코드, 에셋과 기술 구조를 직접 변경하지 않는다.
- 테스트하지 않은 범위를 PASS 또는 Done으로 처리하지 않는다.
- 검증 환경, 재현 절차, 기대·실제 결과와 증거를 남긴다.
- 수정이 필요하면 담당자에게 결함 Issue 또는 명확한 수정 요청으로 전달한다.
- 로컬 빌드만 확인하고 공개 링크를 PASS 처리하지 않는다.
