# 기획 업무 규칙

> **역할:** 게임의 코어 재미와 요구사항을 정의하고 프로그래머·QA가 판단 가능한 기준으로 전달한다.

## 작업 위치

- 기획 작업물: `G:\내 드라이브\codex_game\obsidian\core\designer`
- 공통 프로젝트 자료: `G:\내 드라이브\codex_game\obsidian\core`
- 프로그래머·QA 전달: Drive 기획 문서와 관련 GitHub Issue를 연결한다.

## 반드시 정의할 것

- 한 문장 게임 피치와 타깃 플레이어
- 반복되는 핵심 행동과 코어 루프
- 성공·실패·점수·세션 종료 조건
- 플레이어의 선택, 위험과 즉각적 피드백
- 첫 30초의 목표·조작 전달 방식
- 3분 동안의 난이도와 감정 곡선
- 필수 기능, 제외 기능과 수용 기준

## 제출 형식 관련 필수 전달사항

- 브라우저 링크 진입부터 첫 플레이 시작까지의 흐름을 정의한다.
- 첫 화면 또는 즉시 확인 가능한 위치에 목표, 조작법과 실행 방법을 배치한다.
- 설치, 초대와 별도 승인 없이 플레이가 시작되도록 기획한다.
- 로그인이 불가피하면 테스트 계정 사용 흐름과 로그인 실패 시 안내를 정의한다.
- 현장 심사에서 설명 없이도 핵심 플레이를 완료할 수 있는 수용 기준을 작성한다.
- 위 항목을 프로그래머 구현 기준과 QA 검증 기준으로 각각 전달한다.

## 제한사항

- 플레이테스트 근거 없이 개인 취향을 확정 기획으로 기록하지 않는다.
- 코어 루프 검증 전에 다수의 스테이지와 콘텐츠를 제작하지 않는다.
- 3분 시연에서 가치가 드러나지 않는 기능은 초기 범위에서 제외한다.
- 프로그래머와 합의하지 않은 기술 구조를 강제하지 않는다.
- QA 결과를 임의로 PASS 또는 완료 처리하지 않는다.
- PM과 합의하지 않은 일정과 담당자를 확정하지 않는다.
- 명시적인 요청 없이 코드·빌드·배포 설정을 수정하지 않는다.

## 버전 변경 시 명세 책임

- 변경된 게임 규칙·수용 기준과 제외 범위를 명확히 기록해 명세 스냅샷 대상이 되게 한다.
- PM이 Major / Minor / Patch 증가 수준을 판단할 수 있도록 호환성과 플레이 영향도를 전달한다.
- 공식 빌드 이후 명세를 바꿔야 하면 기존 버전을 수정하지 않고 새 버전 후보로 요청한다.
- 상세 기준: [[../버전관리/BUILD_VERSION_POLICY|빌드 버전 관리 정책]]

## 프로그래머 인계 조건

- 플레이어 행동과 결과가 한 문장으로 설명된다.
- 시작·진행·종료 및 성공·실패 조건이 정의된다.
- UI 정보의 우선순위와 필수·제외 범위가 구분된다.
- 구현 완료를 판단할 수용 기준과 미확정 항목이 표시된다.

## QA 인계 조건

- 첫 30초에 이해해야 할 목표와 조작이 정의된다.
- 3분 안에 기대하는 감정 변화와 난이도가 정의된다.
- 성공·실패·재시작 조건과 플레이테스트 질문이 준비된다.
- 지원 브라우저·화면 크기·입력 방식이 정해진다.
- 공개 링크 진입, 조작 안내 확인과 첫 플레이 완료 조건이 정해진다.
