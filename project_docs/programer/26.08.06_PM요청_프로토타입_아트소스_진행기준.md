## 결론 제안

현재 기획 0.03까지 작동하는 게임을 만드는 데 완성 아트 소스는 필수가 아니다.

프로그래머는 임시 에셋으로 전체 코어 루프를 먼저 구현하고 플레이 검증을 진행할 수 있다. 완성 아트는 기능과 화면 규격이 안정된 뒤 교체하는 방식을 제안한다.

## PM 결정 요청

다음 진행 방식을 승인해 달라.

- 1단계: 임시 에셋으로 카드 펼치기, 종 경쟁, 카드 획득, 개인 카드 선택, 포커 비교, HP와 전투 종료까지 구현
- 2단계: 플레이 가능 프로토타입으로 화면 가독성·조작·코어 재미 검증
- 3단계: 확정된 규격에 맞춰 Aseprite 도트 에셋을 제작·교체
- 완성 아트 미도착을 프로그래밍 착수 차단 조건으로 두지 않음

## 임시 에셋으로 가능한 항목

| 항목 | 임시 구현 방식 |
|---|---|
| 카드 | 텍스트, 단색 도형, 문양·랭크·해골 수 표시 |
| 보드 | Unity 기본 3D Plane과 단색 머티리얼 |
| 벨 | 기본 도형 또는 UI 버튼 |
| 캐릭터 | 단색 실루엣 또는 임시 초상화 |
| FX | Unity 기본 파티클, 색상 변화, 짧은 화면 흔들림 |
| UI | 기본 패널·버튼·폰트 |
| 사운드 | 생략 또는 라이선스가 확인된 임시 클릭음 |

임시 에셋이어도 0.03의 상태 전환과 수용 기준 검증에는 문제가 없다.

## 조기 확정이 필요한 최소 아트 규격

완성 소스보다 아래 규격을 먼저 결정해야 재작업을 줄일 수 있다.

1. 카드 한 장의 기준 픽셀 해상도와 화면 표시 크기
2. 카드 앞면의 문양·랭크·해골 수 배치와 뒷면 규격
3. 고정 보드게임 카메라의 각도·거리·화면 구성
4. Aseprite 공통 팔레트와 픽셀 밀도
5. 저해상도 RenderTexture 기준 해상도
   - 1차 제안: `640×360`
   - 가독성 보완 후보: `960×540`
6. 어두운 기본 조명과 하이라이트 색상 기준
7. 카드·UI·FX 에셋의 파일명, 폴더와 라이선스 기록 방식

## 프로그래밍 적용 원칙

- 게임 판정은 상태 머신과 입력 시각으로 처리한다.
- 물리 충돌은 승패·획득·연출 판정의 기준으로 사용하지 않는다.
- 카드·벨·캐릭터 연출은 Animator, Tween, Particle, Shader와 Audio FX로 표현한다.
- 임시 에셋과 완성 에셋을 교체할 수 있도록 로직과 프레젠테이션을 분리한다.
- 웹 빌드 성능과 가독성을 우선하고 과도한 블룸·안티앨리어싱은 사용하지 않는다.
- 출처와 배포 권한이 확인되지 않은 임시 에셋은 공개 빌드에 포함하지 않는다.

## 일정 영향

- PM 승인 후 완성 아트를 기다리지 않고 코어 기능 구현을 계속할 수 있다.
- 아트 규격 결정이 늦어지면 기능 구현은 가능하지만 UI 배치, 카드 크기, 카메라와 FX 조정에 재작업이 발생할 수 있다.
- 완성 아트를 처음부터 필수 조건으로 두면 프로그래밍과 플레이테스트 시작이 아트 일정에 종속된다.
- 상세 전체 구현 예상은 기존 프로그래머 일정 문서의 0.03 기준 `148~208시간`을 사용한다.
